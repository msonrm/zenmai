# Zenmai PlayStation 版 移植計画

**状態: 段階 1〜4 完了・遊べる**（2026-08-21 更新）。実際に作って分かったことは
**`ps1-implementation-notes.md`** に置いた。以下は着手前に書いた計画で、
**判断の記録として残してある**（設計の方針はほぼそのまま通ったが、開発環境だけは
pcsx-redux + psyqo ではなく「フリースタンディング C を直接 PS-EXE に固める」形に変えた）。

ブラウザ版（https://zenmai.pages.dev/）を PlayStation（初代）へ移植するための計画。
開発環境は [pcsx-redux](https://github.com/grumpycoders/pcsx-redux) を軸に想定する。

## なぜ PS1 か

このプロジェクトは、堀井雄二がコマンド選択式で解いた 2 つの問題
（①家庭用機にキーボードが無い ②プレイヤーが作者の語彙を当てるまで進めない）に、
**制約そのものを外す側から**答えるものだった。

★**PS1 は、まさにその「キーボードの無い家庭用機」そのもの。**
問題を作った側のハードウェアの上で別解を実演できる、というのが移植の意味。

そして ★**入力の設計はもともと DualShock の配置で作ってある**（D-pad ＋ フェイス ＋ L/R）。
ブラウザ版のゲームパッド入力は W3C Standard Gamepad Layout に沿っていて、
これは DualShock の写しなので、**移植というより里帰りに近い**。

## 決めごと

| | 方針 |
|---|---|
| 文字 | 本文 **24×24**、ふりがな **12×12** |
| 言語 | **日本語と英語の両方**（ブラウザ版と同じく、英語＝訳さない＝原作のまま） |
| 権利 | **著作権・商標を侵さない**。同梱物はすべて自由なライセンスのものだけにする |

## 1. 画面 —— ここが最大の設計判断

24×24 ＋ ルビ 12×12 を選ぶと、**画面モードが決まってしまう**。

| モード | ルビ込み（1 行 36px） | ルビ無し（24px） | 1 行の字数 |
|---|---|---|---|
| 640×240（ノンインタレース） | **6 行** | 10 行 | 26 字 |
| 640×480（インタレース） | **13 行** | 20 行 | 26 字 |

★**640×240 では 6 行しか入らない**ので、テキストアドベンチャーとしては狭すぎる。
→ **日本語モードは 640×480 インタレースを既定とする。**

### ★前例: PlayStation の日本語版は「コマンド選択式・1 行 16 字・本文 9 行」だった

商用の PlayStation 日本語版は ★**コマンド選択式**で、画面の左右に装飾領域を持ち、
**本文は 1 行 16 文字 × 9 行**。それでゲームとして成立していた（msonrm さんの記憶）。

★**これはこの企画の位置づけを、そのまま立たせる。** 元々の主題は
「堀井雄二がコマンド選択式で解いた問題への別解」だった。前例が**同じハード・同じ作品で
選択式を採っている**なら、**その隣に別解を並べて見せられる**。
「キーボードの無い家庭用機」という制約に対して、
**片方は入力を諦めて候補を見せ、こちらは入力できるようにして候補を見なくする** ——
比較の図が、実機の上で完成する。

★**384 / 24 = ちょうど 16 字**。PS1 の横解像度は 256/320/384/512/640 なので、
**384×240 に 24×24 を並べるとぴったり合う**。★**前例がまさに 1 行 16 字だった**ので、
**24×24 という寸法自体が商用で通った**ことになり、こちらの選択の裏付けになる。

そして ★**横の制約は思ったよりゆるい**。640 幅（26 字）に固執しなくてよい。

| | 1 行 | 利点 |
|---|---|---|
| 640 幅（現計画） | 26 字 | 一度に読める量が多い |
| **384 幅** | **16 字** | ★**実機で字が鮮明**（PS1 の 640 モードは実機だとにじみやすい） |

★**ただし前例に無い荷物がある —— ふりがな。** 前例は**コマンド選択式**だったので
**読みを見せる必要が薄かった**（選ぶだけなら読めなくても進める）。
このプロジェクトは**自由入力**が芯なので、**画面に出た名前をそのまま打つ**ためにルビが要る。
つまり 16 字/行が成立していたとしても、**そのまま真似ると縦が足りない**
（384×240・ルビ込みだと 6 行 ＝ 96 字しか映らない）。

→ **横は 640 のまま進め、実機のにじみが問題になったら 384（16 字）へ落とす**。
前例があるぶん、この退避は安全だと分かっている。

### ★要件: 1 ターンの出力が画面に収まること

画面の広さは好みではなく**要件**で決まる。訳文 1,427 件を実測した結果:

| 画面 | 容量 | ★収まらない訳文 |
|---|---|---|
| 前例 16×9 | 144 字 | **8 件** |
| 384×480i（16×13） | 208 字 | **2 件** |
| 640×480i（26×13・余白なしの上限） | 338 字 | **2 件** |
| ★**640×480i（24×12・採用＝下記の割り付け）** | **288 字** | **2 件** |

長いほうから **527・349・202・195・195・186・155・153・143…** と並び、
★**極端に長いのは 2 件だけ**で、あとは急に短くなる。そしてその 2 件は**読み物**
（ちらしや碑文のような「読むもの」）。

結論:

- ★**ふつうのターンは、どの構成でも収まる**
- ★**読み物だけは、画面をどれだけ広げても 1 画面に入らない**（最長 527 字）
  → これは**画面設計の問題ではなく、改ページの機構の問題**。前例も必ず改ページしていたはず
- **640×480i で要件は満たせる** —— 読み物 2 件を除いて全部が 1 画面に収まる

★**改ページは「読み物のためだけ」に要る**と分かったので、
通常のターンでは出さない（毎回「続く」が出ると、テンポを落とすだけになる）。

### 画面の割り付け（確定）

ぴっちり詰めると読みにくく、雰囲気も出ない。余白を取る。

| | |
|---|---|
| 画面 | **640×480**（インタレース） |
| 字 | 本文 **24×24** / ルビ **12×12** → **1 行 36px** |
| 左右 | ★**1 文字ぶん空ける**（各 32px）→ **1 行 24 字** |
| 上端 | 詰めてよい |
| 最下行 | ★**コマンド入力に 1 行**（24px。打つのはかなだけなのでルビ不要）→ **本文 12 行** |
| 実効 | ★**24 字 × 12 行 ＝ 288 字** |

★**余白は「ただ」だった。** 288 字でも**収まらないのは同じ 2 件**（読み物）のまま。
訳文の長さは **527・349・202・195…** と並んでいて、★**202 と 349 のあいだに大きな空白**がある。
つまり容量が **203〜348 字のどこにあっても結果は変わらない** ——
いま 288 字なので、**さらに 85 字ぶんを余白に回しても改ページの件数は増えない**。

→ 装飾や行間にもう少し使いたくなったとき、**数字の裏付けを持って使える**。

### ちらつきは「CRT の蛍光体」の現象なので、想定する環境ではほぼ起きない

480i が CRT でちらつくのは、★**1 ドットの横線が片方のフィールドにしか無く、
30 回/秒でしか描かれない**から（漢字の横画はまさにこれに当たる）。
**液晶は画素を保持する**のでこの仕組みが無く、**エミュレータはそもそも
フィールド交互の走査を再現しない**（フレームバッファをそのまま出す）。

そして決定的なのは ★**文字は静止していること**。PS1 の 480i は VRAM 上に
**640×480 の絵を持って** 1 行おきに読み出す方式なので、**絵が止まっていれば
2 つのフィールドは同じ絵から来る** → weave で**元の 480 行が完全に復元される**。
コーミング（ギザギザ）は**フィールド間で絵が動いたとき**に出るもので、
テキストアドベンチャーの画面は deinterlace にとって最も易しい入力になる。

| 環境 | 見込み |
|---|---|
| **エミュレータ** | ★問題なし（ちらつきという現象自体が起きない） |
| **実機 → 液晶**（まともな deinterlacer） | ★静止画は weave されて綺麗。遅延は増える |
| 実機 → 液晶（安価な bob 処理） | わずかに揺れる可能性 |
| **実機 → CRT** | ★リスクが残るのはここだけ |

★**配布はエミュレータ向けを主とする**ので、480i を選ぶ代償は**実質ほぼ払わない**。

- ★**守るべき設計**: **なめらかスクロールを使わない**（動いた瞬間だけフィールド間で
  絵が食い違う）。テキストアドベンチャーは**ページ単位で描き直す**のが自然なので、
  そこを外さなければよい
- 逃げ道（実機 CRT を重く見る場合）: ルビを**別行に逃がす**。
  ★**「初出の語だけルビ」は採らない**（ルビは毎回出すと決めた。§7 参照）

### 英語モードは別のモードでよい

英語は**ふりがなが要らず、欧文は幅が狭い**ので、条件がまるで違う。

- 欧文 **12×24** なら 1 行 **53 字**、640×240 で **10 行**
- ★**インタレースを使わずに済む**ので、英語モードのほうが**字が安定して読みやすい**

→ **言語によって画面モードごと切り替える**。ブラウザ版で「英語＝訳すのをやめる」だけで
済んだのに対し、PS1 では**表示層まで分岐する**のが移植固有の差。

## 2. データ（実測）

現在の配布物から実測した値。★フォントは**この作品が実際に使う字だけ**を積む。

| もの | 大きさ | 備考 |
|---|---|---|
| story file | **84.8 KB** | z3。MIT の ZIL ソースから自前ビルド |
| 訳文アセット | 319 KB（JSON・2026-08-18 実測） | 束ねた二進形式にすれば 6〜7 割に落ちる見込み |
| 入力語彙 | 106 KB（JSON・2026-08-18 実測） | 同上。★語彙の構造化（words = 表記+読み / 上位語宣言）で倍増したが、**増えたのは JSON の冗長さで情報ではない** —— 二進の表に焼けばむしろ旧より縮む。構造化で実行時の逆算（読みの推測・持ち主の逆算）が消えたので、C で再実装する量は減った |
| 本文フォント 24×24 | **87.8 KB** | 全角 **1,249 字**（漢字 **1,096** / かな 138 / 記号 15）× 72 B |
| ルビ 12×12 | **2.4 KB** | かな **138 字** × 18 B |
| 欧文 12×24 | **3.0 KB** | ASCII 84 字 × 36 B |

画面に出る異なり字は全部で **1,333**。合計は圧縮前でも **500 KB 前後**。★**PS1 の主記憶 2 MB に全部載る**（CD からの
読み直しが要らない＝ロード無しで遊べる）。

### VRAM の扱い

PS1 の VRAM は 1 MB。★**フォント全体は VRAM に置けない**ので、
**主記憶に持ち、使う字だけをテクスチャページへ載せる**（LRU のグリフキャッシュ）。
1 画面に出る異なり字はたかだか数百なので、キャッシュで足りる。

### PS1 の組み込みフォントは使えるか

**BIOS は字形を持っている**が、この計画では**漢字のほうは使えない**。

| | 中身 | 判断 |
|---|---|---|
| BIOS の ASCII デバッグフォント | 小さい欧文（`FntLoad` / `FntPrint` 系） | ★**段階 1・2 では使う**（自前フォントを待たずに動かせる） |
| 日本語 BIOS の漢字フォント | 日本語機の BIOS が持つ字形（メモリーカード管理画面などで使う） | ★**使わない** |

漢字を使わない理由:

1. ★**BIOS は Sony の著作物**。字形を取り出して同梱すれば**再配布**にあたる
2. ★**OpenBIOS が使えなくなる**。遊ぶ人に**実機の日本語 BIOS**を要求することになり、
   「起動から自由なもので閉じる」という方針が崩れる
3. **地域依存** —— 漢字を持つのは日本語機の BIOS だけ。北米・欧州機では動かない
4. 実用面でも 16×16 相当で、★**選んだ 24×24 に足りない**（12×12 のルビと組む前提が崩れる）

★**ASCII のデバッグフォントだけは素直に有用**。段階 2（英語版）まではこれで進められるので、
**自前フォントの用意が段階 1 の前提にならない**（依存の根が 1 本ほどける）。
仕上げで自前の欧文 12×24 に差し替える。

### 代案: 16×16 ＋ 8×8 ルビ（採らないが、数字は残す）

★**QuuBee（`~/development/qb`）が同じ問題を先に通っている。** PC-98 エミュレータ向けに
**東雲フォント**（ANK `shnm8x16a/r.bdf` ＝ 8×16 / 漢字 `shnmk16.bdf` ＝ **16×16**）を
1bpp のアトラスへ変換していて、`tools/font_build/makefont.cjs` が **BDF → ビットマップ**の
変換器そのもの。`licenses/fonts/` には**素性を確認済みの自由なフォント**が並んでいる
（東雲・さざなみ・美咲・M+・かっぱ・あゆ・オラダノ・ねこさん）。

つまり ★**「フォントのライセンス確認」はゼロからではない**。16px 系を選ぶなら、
**確認済みの字形と変換器がそのまま使える**。

| | **24×24＋12×12**（採用） | 16×16＋8×8（代案） |
|---|---|---|
| 1 行（余白込み） | 24 字 | **38 字** |
| 行数（入力行を除く） | 12 行（★640×480i が要る） | **9 行（640×240・インタレース不要）** |
| 1 画面 | 288 字 | **342 字** |
| フォント | 87.8 KB | **40.1 KB** |
| 字の出どころ | ★**KH ドットフォントがそのまま使える**（下記で確定） | 東雲 16×16 ＋ 美咲 8×8 |

★**この代案の唯一の利点だった「字がすぐ手に入る」は消えた** —— 24 ドットにも
自由でビットマップのフォントが実在すると分かったため（下記）。残る違いは**密度だけ**になる。

### ★それでも 24×24 を採る理由 —— 16×16 では**要件を満たせない**

代案は「密度が高いだけ」ではなく、**この作品の要件に対して機能的に足りない**。

実測すると、訳文が使う漢字 1,096 字の中に**画数の多い字が実際に含まれている**:

```
絨 毯 蝋 燭 鍮 錆 鍵 籠 響 轟 聾 麗 鎧 髑 髏 臓 顎
```

★**これらはほぼ全部が「物の名前」か「部屋の名前」**である:

| 語 | 役割 |
|---|---|
| **絨毯** | ★**揚げ戸を隠している** —— 最初の関門そのもの |
| 真**鍮**のランタン | 光源。序盤で必ず要る |
| **蝋燭** | 持ち歩いて火を点ける道具 |
| **髑髏** | 宝物のひとつ |
| **轟**音の部屋 | 部屋の名前 |

普通のゲームなら潰れた漢字は**見栄えの問題**で済む。★**この作品では機能の問題**になる ——
**画面に出た名前が、そのまま打つべき語**だから（「画面に出した語は、打てなければならない」）。
16×16 で `絨` `毯` `髏` を描くには筆画の省略・併合が要り、**語を知らない読み手が
「これは何だ」を画面から知る**という遊び方が崩れる。

★**24×24 は、複雑な漢字が描けるようになる寸法**として、プリンタや高解像度表示で
古くから使われてきた標準的なサイズでもある。

→ **代案は「実装が重ければ戻る場所」ではない。** 退くなら、
**字を小さくするのではなく別のところ**（ルビの出し方・行数・画面モード）で調整する。

### ★フォント: KH ドットフォント「日比谷24」で確定できる

| | ★**KH ドットフォント**<br>`jikasei.me/font/kh-dotfont/` | 縁架フォント<br>`enth-imaginary-rail.jp/tools/enkafont/` |
|---|---|---|
| 24×24 | ★**日比谷24（明朝体）** | あり |
| **12×12（ルビ）** | ★**神楽坂12（明朝体）ほか 3 書体** | ★無い（24×24 のみ） |
| 漢字 | ★**JIS 第2水準まで全部** | 教育漢字＋頻度上位 計 1,269 字 |
| ライセンス | **SIL OFL 1.1** | **SIL OFL 1.1** |
| 形式 | TrueType（**ビットマップ埋め込み**） | TrueType（**ビットマップ埋め込み**） |
| 縦書き | 日比谷24 は対応 | 未確認 |

書体の内訳は **12 ドット 3 / 16 ドット 7 / 24 ドット 1 / 32 ドット 1**。
★**24 ドットは「日比谷24（明朝体）」1 書体だけ**なので、選択の余地は無い。

出自は平木敬太郎氏が 1991〜1996 年にデザインした『電脳フォント』（X68000 向けなどで頒布・
ソフトベンダー TAKERU で販売）を、自家製フォント工房が TrueType 化したもの。
★**24 ドット明朝は、まさにこの寸法のために設計されたシステムフォント**で、
散文を読ませるこの企画には素性が合っている。

### ★収録は「規格」で保証される —— 実測で確認済み

縁架の収録基準は**頻度**なので「数は足りても集合が入れ子とは限らない」という穴があったが、
KH は **JIS 第2水準まで全部**＝**規格が基準**なので、
★**こちらが何を使うかと無関係に、規格の内側にいる限り必ずある**。

そこで「使う字が JIS X 0208 の内側にいるか」を実測した:

| | |
|---|---|
| 表示に出る異なり字 | 1,318 字 |
| うち漢字 | **1,096 字** |
| ★**JIS X 0208 の圏外** | ★**0 字**（iso2022-jp / shift_jis / euc-jp のどれで測っても同じ） |

心配していた **髑 髏 絨 毯 鍮 錆 聾 轟 燭 蝋 鎧 顎** —— ★**全部 JIS の内側**。
→ ★**欠字は出ない。「欠けた字を自作する」「かな書きに逃がす」という退避は要らない。**

**唯一の圏外は記号 1 字**、em dash（`—` U+2014）。JIS にある罫線状のダッシュ（`―` U+2015）へ
置き換えれば済む。★**アセット側で正規化しておくこと**（PS1 側で気づくと原因が分かりにくい）。

### ★本文とルビが同じ一族で揃う

これが KH を採る 2 つめの決め手。**明朝体が 24（日比谷24）と 12（神楽坂12）の両方にある**ので、
**本文とルビの字形が調和する**。縁架は 24×24 しか無いため、ルビ用 12px を別フォントから
持つことになり、★**ライセンスの両立**と★**字形の不一致**という手間が 2 つ生える。

### ★明朝体 × 480i —— 既知のリスクが濃くなる升目

★**明朝体は 480i のちらつきにとって最悪の字種。** §1 で「ちらつきは 1 ドットの横線が
片フィールドにしか無いことで起きる」と整理したが、**明朝体の横画はまさに 1 ドットで細い**。

ただし**新しいリスクではない** —— リスクが残るのは元々**実機 CRT の升目だけ**で、
エミュレータと液晶では現象自体が起きない。**その升目だけが濃くなる**。

- 配布はエミュレータ向けが主なので、★**代償は実質ほぼ払わない**
- 実機 CRT を重く見るなら、**太めの字種**が要る。24 ドットに他の書体は無いので、
  そのときは**縁架**（別の素性）か、16 ドット系の**秋葉原16（丸ゴシック）**へ落ちる
  ＝ §1 の「384 幅へ落とす」退避と同じ方向

### 字を同梱するという、ブラウザ版には無かった責任

ブラウザ版は**端末のフォントを借りていた**ので考えなくてよかったが、
PS1 版は ★**字の形を同梱物として持つ**ことになる。
**「無料で使える」と「再配布できる」は別物**なので、条文で確認するのが要件だった。

→ ★**KH ドットフォントは SIL OFL 1.1** なので、**埋め込みと再配布が明示的に許される**
（表示義務あり・単独販売禁止・派生は SIL 継承）。**ラスタライズも不要**
（ビットマップが埋め込まれている）ので、**「変換したものを配ってよいか」という
一段ややこしい問いにも入らずに済む**。
